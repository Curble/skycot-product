# nondev fork — operator guide

This folder holds the tooling that keeps our fork of **T3 Code** healthy. It is written for the
operator (a CEO, not a developer). Technical terms are expanded the first time they appear.

## 1. What this repository is

- **Upstream** = the original project, `pingdotgg/t3code` on GitHub. It moves fast: roughly
  **55 commits (saved changes) per day**, all squashed, so its history is one straight line.
- **This repo** (`mark-hallam/t3code-nondev`) is an **in-place fork**: a full copy of upstream
  plus a short tail of our own commits on top. We **never rewrite history** (no `rebase`, no
  force-push to `main`); we **merge** upstream into ours.
- **Our product** is a simpler client ("Simple mode") served at **`/simple/`** beside the stock
  T3 Code UI, which stays available as "Advanced mode". The engine (server, providers, desktop
  shell) is upstream's, unchanged.

Glossary used below:

- **Merge** — git combining two lines of history into one. **Conflict** — both sides changed the
  same lines and someone has to choose.
- **Seam** — a place where our code has to touch an upstream file. Every seam is a future
  conflict, so we keep them tiny and list every one in `SEAM-MANIFEST.md` at the repo root.
- **Lockfile** (`pnpm-lock.yaml`) — the exact list of every dependency version. Regenerated by the
  package manager, never edited by hand.
- **Typecheck** — the TypeScript compiler checking that our code still fits upstream's "shapes".
  It is our early-warning alarm when upstream renames or removes something we use.
- **PR (pull request)** — a proposed change on GitHub with its own checks and a Merge button.
- **CI (continuous integration)** — GitHub Actions running checks automatically on every PR.
- **`vp`** — Vite+ (pronounced "vite plus"), the command runner upstream uses; it wraps `pnpm`.

## 2. Folder rules — where our code may live

Our code lives **only** in paths upstream does not own. Anything there can never conflict.

| Path                             | What goes there                                      |
| -------------------------------- | ---------------------------------------------------- |
| `apps/nondev/**`                 | our client (the workspace package `@t3tools/nondev`) |
| `nondev/**`                      | this folder: tooling, scripts, docs, brand assets    |
| `docs/nondev/**`                 | design docs for the fork                             |
| `.github/workflows/nondev-*.yml` | our GitHub Actions                                   |
| `SEAM-MANIFEST.md` (repo root)   | the list of upstream files we were forced to edit    |

Every edit to any **other** file is a seam and **must** have a row in `SEAM-MANIFEST.md` with a
marker comment (`// nondev-seam: <id>`) in the file. `node nondev/scripts/check-seams.ts` enforces
this and runs in CI. Format and rules: `nondev/SEAM-MANIFEST.template.md`.

Rule of thumb: if a change _could_ be made inside `apps/nondev/**` instead, make it there.

## 3. How a nightly sync works

Every night at **03:00 Melbourne** (02:00 outside daylight saving) the workflow
`.github/workflows/nondev-sync.yml` runs `nondev/scripts/upstream-sync.ts`, which:

1. Fetches upstream and creates a branch `sync/upstream-YYYY-MM-DD` from `main`.
2. Merges `upstream/main` into it. `git rerere` is on, so a conflict we resolved once is resolved
   the same way automatically next time.
3. Resolves conflicts by rule:
   - `pnpm-lock.yaml` → take upstream's, then `vp install --lockfile-only` re-adds our deps.
   - a file listed in `SEAM-MANIFEST.md` → take upstream's version and record **"seam needs
     re-apply"** with our diff in the report.
   - a path we own → keep ours, flag it.
   - **anything else** → abort. The branch is deleted, nothing changes, the run fails loudly.
4. Installs, typechecks and builds `@t3tools/nondev`.
5. Writes `nondev/sync-report.md` (commits merged, version moved from→to, conflicts and how each
   was resolved, seams to re-apply, check results, and a list of upstream **exports we import
   that were removed or renamed**, so the fix location is known before reading the typecheck log).
6. Pushes the branch and opens or updates the PR **`sync: upstream YYYY-MM-DD`**, label
   `upstream-sync`, with the report as the PR body. Red syncs also get `needs-human`.
7. If the repository variable `NONDEV_SYNC_AUTOMERGE` is `true` **and** the sync was clean,
   it enables GitHub auto-merge, which merges once CI (`nondev / check`) is green.

Run it yourself from a clean checkout (no uncommitted changes, otherwise it refuses):

```bash
node nondev/scripts/upstream-sync.ts --dry-run        # just report what would happen
node nondev/scripts/upstream-sync.ts                  # do it, land on the sync branch
node nondev/scripts/upstream-sync.ts --no-verify      # skip install/typecheck/build
node nondev/scripts/upstream-sync.ts --branch sync/try-again
```

Exit codes: `0` clean (or nothing to merge), `1` merged but needs a human, `2` aborted/refused.

## 4. When the sync PR is red

Open the PR body (it is the report). The **Verdict** line names the reason. Three cases:

### Case A — "lockfile re-resolution failed"

Meaning: upstream removed or renamed a dependency version (a "catalog" entry) that
`apps/nondev/package.json` relies on. Fix: on the sync branch, adjust the dependency in
`apps/nondev/package.json` to what upstream now provides (check `pnpm-workspace.yaml` → `catalog`),
run `vp install --lockfile-only`, commit `pnpm-lock.yaml`, push. CI re-runs.

### Case B — "N seam(s) need re-applying"

Meaning: upstream rewrote the same lines as one of our seams; the script kept **upstream's**
version so the build stays honest. The report shows our original change as a diff under
"Seams needing re-apply". Fix: on the sync branch, re-add the one or two lines (keep the
`// nondev-seam: <id>` marker), run `node nondev/scripts/check-seams.ts --working-tree --strict`,
commit, push. If upstream restructured the file so the change no longer fits, that is a design
question — ask before inventing a bigger seam.

### Case C — "typecheck failed" or "build failed"

Meaning: upstream changed a contract (a shared type or function) our client uses. Look first at
the report section **"Removed/renamed exports we import"** — it names the module and symbol.
Fix in `apps/nondev/src` only, never by editing upstream packages. Then
`vp run --filter @t3tools/nondev typecheck`, commit, push.

Expect about 1–3 of these per week; each is normally a 5–30 line change. That is the recurring
price of any fork and cannot be designed away — only caught early, which is why the sync is nightly.

### "Merge aborted" (no PR was opened)

A conflict happened in an upstream file that is **not** in the manifest, meaning someone edited an
upstream file without declaring it. Either revert that edit on `main` or add it to
`SEAM-MANIFEST.md`, then re-run the workflow (Actions → "nondev / upstream sync" → Run workflow).

## 5. How to release

Versions are `v<upstream-version>-nondev.N`, for example `v0.1.1-nondev.3`:

- `<upstream-version>` is upstream's number in `apps/desktop/package.json` **at the commit we
  merged** — we never edit version fields in upstream files (it would conflict every release).
- `N` counts our releases on that upstream version, starting at 1.

Steps:

1. Pick a `main` commit whose last sync PR was green (the nightly sync + green CI _is_ the release
   candidate, mirroring upstream's "nightly is the release candidate" rule).
2. `git tag v0.1.1-nondev.3 <commit> && git push origin v0.1.1-nondev.3`
3. The release workflow (to be added as `.github/workflows/nondev-release.yml`) builds desktop
   artifacts and publishes a GitHub Release **in this repository**. Never run upstream's
   `release.yml` — it pushes version bumps, publishes the `t3` npm package and deploys upstream's
   hosting.
4. Because the suffix is not `-nightly.` or `-preview.`, upstream's updater code treats the build
   as a stable channel, and electron-updater compares `0.1.1-nondev.3 → 0.1.1-nondev.4 →
0.1.2-nondev.1` correctly. Verify once with upstream's mock update server
   (`T3CODE_DESKTOP_MOCK_UPDATES`, `vp run start:mock-update-server`) before the first public build.

## 7. GitHub settings the workflows need (one-time)

- **Secret `NONDEV_SYNC_TOKEN`** (recommended): a fine-grained personal access token with
  _Contents: write_ and _Pull requests: write_ on this repo. Without it, PRs created by the bot do
  not trigger CI, so auto-merge can never go green. If you skip it, enable _Settings → Actions →
  General → "Allow GitHub Actions to create and approve pull requests"_.
- **Variable `NONDEV_SYNC_AUTOMERGE`** = `true` only once you trust the checks. Leave unset to
  review every sync PR by hand.
- **Settings → General → "Allow auto-merge"** must be on for the auto-merge step.
- **Branch protection on `main`** requiring the status check **`nondev / check`** (from
  `nondev-ci.yml`). Without it, auto-merge would merge immediately instead of waiting for CI.
- Labels `upstream-sync` and `needs-human` are created automatically.
